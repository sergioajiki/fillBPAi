Etnia do paciente

Planilhas novas trazem a coluna "Etnia do Paciente" — quase sempre vazia, preenchida quando a raça é Indígena. Este documento registra o estudo de impacto, a tabela oficial de códigos fornecida pelo usuário e o plano técnico já aprovado para preencher, pela primeira vez, o campo `prd-etnia` do BPA-I — hoje sempre em branco.

Área: Importação de planilhas · Geração BPA-I Status: Plano aprovado — implementação a seguir Data: 10/09/2026 Módulos afetados: ColunaAliasUtils · LinhaImportacaoDTO · Paciente · AtendimentoProcessor · ValidacaoPlanilhaService · GeradorBPAiService · EtniaUtils (novo)

Contexto

Quando RACA_PACIENTE == "INDIGENA", a nova coluna "Etnia do Paciente" traz o nome da etnia (texto livre, digitado como veio da planilha). Esse texto precisa ser persistido no banco; na geração do BPA-I, precisa virar o código numérico/alfanumérico de 4 caracteres do layout oficial.

Achado-chave: o campo já existe, sempre em branco

Lendo GeradorBPAiService.montarRegistro (seq 22, prd-etnia, 4 caracteres): hoje é sempre padRightSpaces("", 4) — hardcoded em branco, nunca preenchido. O próprio aviso RACA_INDIGENA (AtendimentoProcessor.verificarRacaIndigena) já dizia "é necessário verificar a etnia do paciente" — a lacuna já era conhecida. Esta é a primeira vez que há dado real pra preencher esse campo.

A tabela fornecida pelo usuário

Arquivo tab ind.docx — 6 páginas, cada uma um print da tabela oficial "Código | Descrição". Extraídas (um .docx é um .zip) e lidas nesta sessão. Dois achados moldam o desenho técnico:

Faixa de códigoFormatoExemplo
0001–0334Numérico, com lacunas (ex.: 0325 não existe)0032;BANIWA (BANIUA, BANIVA, WALIMANAI, WAKUE)
X265–X411Alfanumérico, prefixo "X", também com lacunasX401;YANOMAMI

Os dois formatos têm exatamente 4 caracteres — confirma por que o campo já é tratado como ALFA (padRightSpaces) e não NUM no código de geração; um código zero-padded à esquerda quebraria os códigos com prefixo "X".

A coluna "Descrição" já embute variações de nome entre parênteses — mesmo padrão de "apelidos" já usado em medicos_cns.csv: um código, vários nomes aceitos. O CSV novo indexa cada nome (principal e cada variação) como uma linha própria apontando pro mesmo código.

Sem carimbo de origem

O .docx não tem título, fonte nem data de versão registrada nos metadados (só que foi criado pelo usuário nesta sessão) — não há um "carimbo" de origem pra citar além de "tabela fornecida pelo usuário". Não há linha de "não informado/ignorado" na tabela — reforça que o fallback natural é campo em branco.

Decisões fechadas com o usuário

1 · Etnia sem correspondência

Avisa e deixa o campo em branco — não bloqueia a geração do BPA-I. Mesmo padrão do código IBGE não resolvido.

2 · Coluna obrigatória

Toda planilha passa a ter a coluna "Etnia do Paciente" no cabeçalho — mesmo comportamento que RACA_PACIENTE/SEXO_PACIENTE já têm hoje (coluna sempre presente, célula quase sempre vazia).

3 · Validação cruzada

Só no sentido já existente (indígena sem etnia informada) — sem checar o sentido inverso (etnia informada sem raça indígena).

Onde o valor é armazenado vs. convertido — mesmo padrão que raca já usa: o banco guarda o texto digitado na planilha; a conversão pro código de 4 caracteres acontece só na hora de gerar o BPA-I, em GeradorBPAiService. Nenhuma resolução de código acontece na importação — só uma checagem de "isso bate com a tabela?" pra gerar o aviso.

Plano técnico

  1. dados/etnias_indigenas.csv (novo) + EtniaUtils (novo)

    CSV codigo;nome, uma linha por nome aceito (principal + cada variação entre parênteses), construído a partir da transcrição das 6 imagens. EtniaUtils no pacote util, mesmo esqueleto de IbgeUtils mas mais simples (sem fallback de rede): resolver(nomeEtnia) carrega o CSV uma vez (lazy) e busca por nome normalizado (sem acento, uppercase).

  2. Planilha → DTO

    colunas_aliases.csv: ETNIA_PACIENTE;ETNIA DO PACIENTE. LinhaImportacaoDTO ganha o campo etniaPaciente. ExcelImportService.importarLinha ganha uma linha de leitura — mesmo padrão dos outros 24 campos.

  3. Persistência

    Paciente: @Column(name = "etnia", length = 100) + getter/setter — aditivo, migra sozinho (hibernate.hbm2ddl.auto=update). AtendimentoImportacaoService.buscarOuCriarPaciente: .setEtnia(dto.getEtniaPaciente()) nos dois branches (criar/atualizar), ao lado de raca/sexo.

  4. Validação — dois avisos independentes, sem sobreposição

    Nova constante ErroValidacao.ETNIA_NAO_ENCONTRADA (AVISO). verificarRacaIndigena passa a só avisar quando a etnia vier em branco (pedindo pra preencher); quando vier preenchida, nenhum aviso daqui. Um segundo aviso, independente de raça, dispara sempre que a etnia vier preenchida mas não bater com a tabela — em AtendimentoProcessor (importação real) e em ValidacaoPlanilhaService ("Analisar Planilha"), mesmo padrão duplicado que CNS/raça indígena já seguem hoje.

  5. Geração do BPA-I

    Novo método em GeradorBPAiService, espelhando formatarRaca: 

    private String formatarEtnia(String etnia) {
    if (etnia == null || etnia.isBlank()) return padRightSpaces("", 4);
    String codigo = EtniaUtils.resolver(etnia);
    return codigo != null ? codigo : padRightSpaces("", 4);
}

    Em montarRegistro, seq 22 passa de padRightSpaces("", 4); // etnia para formatarEtnia(paciente != null ? paciente.getEtnia() : null).

Testes planejados

ClasseCobre
EtniaUtilsTestnomes conhecidos (principal e uma variação) resolvem pro mesmo código; nome desconhecido → null; normalização de acento/caixa
AtendimentoProcessorTestindígena + etnia em branco → aviso; indígena + etnia reconhecida → sem aviso; etnia preenchida não reconhecida → ETNIA_NAO_ENCONTRADA
ValidacaoPlanilhaServiceTestmesmo caso de etnia não reconhecida, via validar()
GeradorBPAiServiceTestformatarEtnia/seq 22 — reconhecida vs. em branco/não reconhecida
AtendimentoImportacaoServiceTestimportação fim a fim persiste o texto da etnia em Paciente

Nenhum teste depende de rede — a tabela é só CSV, sem fallback externo, mesmo espírito dos testes de IbgeUtils/CnsProfissionalUtils já existentes.
