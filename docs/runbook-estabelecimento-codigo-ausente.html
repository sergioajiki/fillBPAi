Estabelecimento sem código reconhecido ✓ Implementado (Opção C)

Relato do usuário: a coluna Estabelecimento é separada em código + nome na importação, mas nada avisa quando a célula não traz os dois itens. Quando o separador não é encontrado, o código sai vazio — e, antes desta implementação, isso era suficiente para o estabelecimento inteiro (nome incluído) ser descartado em silêncio.

Área: AtendimentoProcessor · AtendimentoImportacaoService · EstabelecimentoRepository · ValidacaoPlanilhaService Status: Implementado (Opção C — aviso + reaproveitamento por nome) — mvnw.cmd test passando (274 testes) Data: 24/09/2026

Contexto

AtendimentoProcessor.separarEstabelecimento(dto) chama StringUtils.separarCodigoENome(valor) sobre o valor cru da célula ESTABELECIMENTO, esperando o formato "CÓDIGO - NOME" (separador reconhecido por regex: hífen comum, en dash ou em dash — [-–—]). 

public static String[] separarCodigoENome(String valor) {
    if (valor == null || !valor.matches(".*" + SEPARADOR_REGEX + ".*")) {
        return new String[]{null, valor};
    }
    String[] partes = valor.split(SEPARADOR_REGEX, 2);
    String codigo = partes[0].trim();
    String nome = partes[1].trim();
    return new String[]{codigo, nome};
}

Quando a célula não contém nenhum separador reconhecido, o método devolve {null, valorOriginal} — o nome é preservado corretamente (o texto inteiro da célula vira o nome), só o código sai nulo. Até aqui, nenhuma informação é perdida — o problema está um passo adiante.

O que quebra de verdade ✓ Corrigido

Descrição do problema como estava antes desta implementação — ver Plano técnico para o que corrige cada ponto.

🛑 O nome corretamente extraído é jogado fora

AtendimentoImportacaoService.buscarOuCriarEstabelecimento(dto) trata código nulo/vazio como "não há estabelecimento nenhum" e devolve null — sem nunca olhar para o nome que separarEstabelecimento preservou corretamente: 

private Estabelecimento buscarOuCriarEstabelecimento(LinhaImportacaoDTO dto) {
    if (dto.getCodEstabelecimento() == null || dto.getCodEstabelecimento().isBlank()) {
        return null;
    }
    ...
}

O atendimento é persistido com estabelecimento = null. O nome que estava certo na célula (ex.: só "UBS CENTRAL", sem prefixo numérico) nunca chega a ser usado em lugar nenhum — nem salvo, nem logado.

Nenhum aviso existe hoje para este caso

Diferente de raça, situação de rua e "paciente sem CPF" — que já emitem AVISO/ERRO quando o valor não é reconhecido — ValidacaoPlanilhaService não tem nenhuma regra para Estabelecimento (confirmado: nenhuma ocorrência do termo no arquivo). O usuário não vê nada no relatório de análise nem no log de importação; a única pista é uma coluna "Estabelecimento" em branco na tela, sem explicação.

Escopo real do dano — não afeta o arquivo BPA-I

Estabelecimento não é escrito no registro BPA-I gerado (o campo do layout relacionado a unidade é AtendimentoBPAi.cnesNts, preenchido por outro fluxo). Estabelecimento hoje serve só para o relatório/organização interna na tela (RelatorioController, coluna "Estabelecimento", via LEFT JOIN FETCH a.estabelecimento). Ou seja: a perda é real, mas fica confinada ao relatório interno do Núcleo — não corrompe o arquivo enviado ao DATASUS. Isso muda a prioridade em relação aos achados de raça/especialidade, mas não torna o problema aceitável: o Núcleo perde a capacidade de saber em qual unidade o atendimento ocorreu, silenciosamente.

Terceira vez que esse padrão aparece nesta sessão

Raça (valor não reconhecido → 99 em silêncio, corrigido), especialidade ("Médico X" → SIGTAP errado em silêncio, corrigido) e agora estabelecimento (nome não reconhecido → registro descartado em silêncio) são a mesma categoria de problema: um separar*/normalizador aceita qualquer entrada sem reclamar quando o formato não bate com o esperado. Vale considerar, depois deste caso, um levantamento pontual dos demais pontos de entrada da planilha que ainda não têm essa cobertura — não é o foco deste runbook, só um registro para não perder de vista.

Opções de solução

Opção A — Aviso apenas, sem mudar o modelo

Nova constante ESTABELECIMENTO_SEM_CODIGO (AVISO, não bloqueante, mesmo padrão de SITUACAO_RUA_INVALIDA/PACIENTE_SEM_CPF_INVALIDO). Emitida em dois pontos, mesmo par já usado para as outras regras:

  • ValidacaoPlanilhaService — ao validar a planilha ("Analisar Planilha"), avisa por linha quando a célula Estabelecimento está preenchida mas não contém um separador reconhecido.
  • AtendimentoProcessor.separarEstabelecimento() — devolve um aviso na lista de warnings da importação real, para o mesmo caso.

Comportamento de dados não muda: o atendimento continua sendo salvo sem vínculo de estabelecimento. A diferença é que o usuário passa a ser avisado — pode corrigir a planilha (acrescentar o código) antes de reimportar. Simples, sem risco, consistente com a cautela já registrada sobre não inventar chaves de identidade que não sobrevivem a uma nova importação (mesmo motivo pelo qual o CPF sintético de Medico foi sinalizado como frágil).

Opção B — Reaproveitar Estabelecimento existente pelo nome

Acrescentar EstabelecimentoRepository.buscarPorNome(String nome) (busca normalizada, mesmo estilo de TextoUtils.normalizar). Quando o código vier ausente mas o nome bater com um estabelecimento já cadastrado (de uma importação anterior com código correto), reaproveita o registro existente — o atendimento fica vinculado corretamente sem precisar do código nesta linha.

Não resolve o caso de estabelecimento realmente novo

Se o nome também não existir ainda no banco, não há para onde apontar — a coluna codigo de Estabelecimento é chave natural (unique=true, nullable=false); não dá para persistir um estabelecimento sem código só com base no nome sem alterar esse modelo. Neste caso o comportamento cai de volta para a Opção A (aviso, sem vínculo).

Opção C — A + B combinadas ✓ Implementada

✓ Implementado — Opção A + Opção B

Sempre emite o aviso da Opção A quando o código não é reconhecido, e adicionalmente tenta o reaproveitamento por nome da Opção B antes de desistir. Resultado prático: quando o estabelecimento já existe no banco (o caso mais comum — a mesma unidade normalmente aparece em várias planilhas ao longo do tempo), o vínculo é recuperado automaticamente e o aviso serve só como registro do que aconteceu; quando é um estabelecimento genuinamente novo sem código em lugar nenhum, o atendimento fica sem vínculo como antes, mas o usuário é avisado e pode agir.

Plano técnico ✓ Implementado

  1. Nova constante de aviso

    ErroValidacao.ESTABELECIMENTO_SEM_CODIGO (AVISO), mesmo padrão das constantes de aviso existentes.

  2. Validação pré-importação

    Regra 8 em ValidacaoPlanilhaService.validarLinha(): célula Estabelecimento não vazia mas sem separador reconhecido (StringUtils.separarCodigoENome()[0] == null) → AVISO por linha.

  3. Importação real

    AtendimentoProcessor.separarEstabelecimento() passou a devolver List<String> — acrescenta o mesmo aviso à lista de avisos do processador quando partes[0] vem nulo mas o valor original não é vazio.

  4. Busca por nome antes de desistir

    EstabelecimentoRepository.buscarPorNome(String nome) (comparação em memória via TextoUtils.normalizar — tabela pequena, unidades do Núcleo) + AtendimentoImportacaoService.buscarOuCriarEstabelecimento() tenta essa busca quando o código está ausente, antes de retornar null.

Decisões em aberto

✓ 1 · Decidido — Opção C

Aviso sempre emitido + reaproveitamento por nome quando o estabelecimento já existe no banco. Ver Plano técnico.

2 · Estabelecimento novo sem código nenhum

Se essa situação for frequente na prática, pode valer permitir cadastro manual do estabelecimento (código atribuído pelo Núcleo) em vez de só avisar — mas isso é uma funcionalidade nova de cadastro, fora do escopo deste runbook. Hoje o atendimento fica sem vínculo, com aviso.

3 · Levantamento geral de "separar*"

Registrado na seção O que quebra de verdade: este é o terceiro caso do mesmo padrão (raça, especialidade, agora estabelecimento). Vale um passe futuro pelos demais pontos de entrada da planilha para ver se há mais algum caso parecido — não é necessário agora, só para não esquecer.
