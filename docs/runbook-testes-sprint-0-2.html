Contexto

O fillBPAi não tinha nenhum teste automatizado — pom.xml sem JUnit/AssertJ/Mockito, src/test/ inexistente. Uma varredura completa do código (docs/DOCUMENTACAO_TECNICA.md) mapeou as 37 classes atuais e serviu de base para montar um cronograma em 5 sprints, priorizando o que é testável sem infraestrutura pesada primeiro (utilitários puros, planilha) e deixando banco e JavaFX para depois. Este runbook é atualizado a cada sprint — cobre, até aqui, infraestrutura, utilitários puros, leitura/validação de planilha Excel, persistência em H2 e a geração do arquivo BPA-I.

Como funciona a automação

"Automatizado" cobre três coisas diferentes que vale separar: o framework que roda os testes sozinho, quem dispara essa execução, e o que ainda não existe (pipeline de CI).

O framework

JUnit 5 (com AssertJ para as verificações) é o framework de teste. Um teste é um método Java anotado com @Test; o JUnit descobre esses métodos sozinho, via reflexão, e executa cada um isoladamente, sem intervenção manual. Uma vez escritos, os 189 testes rodam sempre da mesma forma e cada um termina em passou/falhou sozinho.

Quem dispara a execução

O Maven Surefire (plugin adicionado ao pom.xml no Sprint 0) é quem efetivamente roda o JUnit e recolhe o resultado, acionado por mvn test. Dentro de uma sessão do Claude Code neste projeto, existe também um hook (PostToolUse, documentado no CLAUDE.md) que dispara mvn test sozinho a cada arquivo editado — foi assim que os testes foram validados incrementalmente durante a implementação de cada sprint.

O que ainda não existe

Não há pipeline de CI no repositório (sem .github/workflows/) — hoje os testes não rodam sozinhos a cada git push. Eles rodam quando alguém chama mvn test manualmente, ou dentro de uma sessão do Claude Code via o hook. Um GitHub Actions workflow rodando a suíte a cada push/PR é uma opção futura, não implementada até aqui.

Organização

src/test/java/br/gov/ses/fillbpai/ espelha exatamente a estrutura de src/main/java/ — cada classe testada tem sua *Test.java no mesmo pacote. 21 classes de teste, 189 métodos @Test.

mvnw.cmd test -Dtest=CepUtilsTest          # roda só uma classe

Decisões de arquitetura aprovadas antes da implementação

1 · Seam de caminho configurável em ColunaAliasUtils

ColunaAliasUtils grava direto num caminho de arquivo fixo no código (src/main/resources/dados/colunas_aliases.csv) — o CSV real do projeto. Um teste que chamasse salvar/remover sem cuidado teria corrompido esse arquivo. A constante CAMINHO_CSV_FONTE virou um campo caminhoCsvFonte configurável, com um método pacote-privado usarCaminhoParaTeste(String) usado só pelos testes — o comportamento em produção não muda (continua apontando para o caminho real por padrão). ColunaAliasUtilsTest aponta para um arquivo em @TempDir antes de cada teste e restaura o caminho real depois.

2 · Refactor de GeradorBPAiService — adiado para o Sprint 4

O mesmo problema existe em GeradorBPAiService (acoplado a FileChooser) e em CnsProfissionalUtils (mesmo padrão de caminho fixo do ColunaAliasUtils) — os dois refactors já foram aprovados, mas nenhuma das duas classes entra no Sprint 0-2 (a primeira é testada no Sprint 4, a segunda no Sprint 5).

Sprint 3 — Persistência (H2 em memória)

Nova persistence unit de teste, bpaPU-test (src/test/resources/META-INF/persistence.xml), apontando para jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1 com hibernate.hbm2ddl.auto=create-drop — cada teste abre e fecha sua própria EntityManagerFactory, recriando o schema do zero e isolando testes entre si sem precisar limpar tabelas manualmente. Nenhum arquivo de produção precisou mudar neste sprint. 17 testes.

Achado — tipo de exceção perdido no wrapping

AtendimentoImportacaoService.importar() lança IllegalStateException internamente para estrutura de planilha inválida, mas o próprio método tem um catch (Exception e) genérico que recaptura e reembala qualquer exceção como RuntimeException("Erro na importação: " + e.getMessage()) antes de propagar. Quem chama importar() nunca recebe o tipo original — só a mensagem, aninhada dentro da nova. O teste foi ajustado para verificar o comportamento real (RuntimeException com a mensagem esperada dentro), não o que o código interno sugere à primeira leitura. Nenhuma mudança de código foi feita — é só um registro do comportamento observado.

Sprint 4 — Geração do BPA-I

Refactor aprovado executado: extraídos gerarConteudoParcial e gerarConteudoCompleto de GeradorBPAiService — dois métodos pacote-privados que recebem a lista de atendimentos já pronta e devolvem o conteúdo do arquivo como String, sem tocar EntityManager nem FileChooser. Os dois métodos públicos existentes viraram wrappers finos: montam a lista, validam, chamam o método novo e gravam o resultado com Files.writeString(..., StandardCharsets.ISO_8859_1) — mesmo comportamento observável no app desktop de antes. 12 testes, nenhum precisa de banco de dados (confirmado lendo o código: montarRegistro nunca acessa a.getMedico(), só campos do próprio atendimento e de paciente/endereço).

Achados — três divergências reais entre documentação e código, corrigidas

Somando os 39 campos de montarRegistro à mão: 350 caracteres de conteúdo, batendo com o comentário da própria classe (REGISTRO: 352 caracteres com CRLF) — README/CLAUDE.md diziam 340 e "38 campos". Também corrigido: a competência do BPA-I (calcularCompetencia) é o mesmo mês do atendimento — a doc dizia "+1 mês (mês de faturamento)", mas não há nenhuma soma no código, em nenhum dos pontos onde a competência é calculada. E o sequencial dentro da folha reinicia ao passar de 99 registros (mais a troca de folha) — a doc dizia "a cada 20 registros". As três foram corrigidas no README.md e no CLAUDE.md nesta rodada, com o código como fonte da verdade.

Achado — checksum do header pode estourar overflow de int

calcularSomaVerificacao chama Integer.parseInt no SIGTAP de cada atendimento sem proteção contra overflow. Um SIGTAP de 10 dígitos que comece com um valor alto (acima de ~2.147.483.647) lançaria NumberFormatException e quebraria a geração do header inteiro. Não é um problema introduzido pelo refactor — já existia antes — e não foi corrigido nesta rodada (fora do escopo pedido), só registrado.

Sprint 5 — Utilitários com dependência externa

Último sprint do cronograma original. Mesmo seam de caminho configurável já usado em ColunaAliasUtils (Sprint 2), agora também em CnsProfissionalUtils. Em IbgeUtils, buscarPorNome/buscarPorCep/normalizar já eram pacote-privados — testáveis direto, sem precisar de seam. 24 testes, nenhuma chamada de rede em nenhum deles (confirmado pelos logs da execução: só menções a CSV/cache, nunca a ViaCEP).

Detalhe de isolamento — cache de CEP sem reset

IbgeUtils não tem um limparCache() equivalente ao das outras classes de utilitário — cacheViaCep é estático e persiste entre todos os testes da suíte (mesma JVM). Os testes que gravam no cache usam um CEP fake exclusivo ("00000001"), nunca reaproveitado, para não colidir com nada mais na suíte.
