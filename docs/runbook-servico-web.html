Do desktop ao serviço web

Com a demanda crescendo para outros pontos de atendimento, considerou-se transformar o fillBPAi num serviço web — com upload da planilha e download do BPA-I pelo navegador, em vez de instalação local. Este documento levanta o que já é reaproveitável no código atual, o que precisa mudar, e como organizar isso no(s) repositório(s).

Contexto

Hoje o fillBPAi é uma aplicação desktop JavaFX de instalação local, usada pelo Núcleo de Telessaúde de MS: um usuário, uma máquina, um arquivo H2 local. Com mais pontos de atendimento precisando importar planilhas e gerar BPA-I, a instalação local para de escalar — cada posto novo significa instalar Java, o app, e replicar o cadastro de CNS de médicos e aliases de coluna manualmente.

A demanda mínima é: alguém abre uma página, envia a planilha .xlsx, e baixa o .txt do BPA-I gerado — sem instalar nada. O restante deste documento parte do código real do projeto para avaliar o que isso custa.

Achados no código atual

A notícia boa: a camada de negócio não depende de JavaFX. A notícia que exige trabalho: a camada de geração de arquivo e a camada de persistência foram escritas assumindo um único usuário, um único processo de UI.

CamadaEstado atualReaproveitável no web?
ExcelImportService · ValidacaoPlanilhaService · AtendimentoImportacaoService Sem import de JavaFX; recebem String caminhoArquivo, leem via FileInputStream Sim, sem alteração — grava o upload num arquivo temporário e chama do mesmo jeito
model · repository · util (CnsProfissionalUtils, ColunaAliasUtils, CepUtils, etc.) JPA puro / utilitários de arquivo, nenhuma dependência de UI Sim, sem alteração
GeradorBPAiService gerarArquivoComFileChooser(Window, ...) e a versão completa recebem javafx.stage.Window e escrevem direto no arquivo escolhido pelo FileChooser Precisa refatorar — separar "montar o conteúdo BPA-I" (retorna bytes) de "escolher onde salvar" (é só a UI desktop que precisa disso)
DatabaseInitializer Um único EntityManager criado na inicialização e reusado pela vida toda do app, acessado direto por MainController/RelatorioController Precisa redesenhar — EntityManager não é thread-safe; web com requisições concorrentes exige um por requisição
MainController · RelatorioController · ConfiguracoesDialog Estado de tela (filtro, seleção, competência) e navegação amarrados ao ciclo de vida do Stage JavaFX Não reaproveitável — é a própria UI, reescrita como frontend web

Achado de segurança, não só de arquitetura

DatabaseInitializer.iniciar() sobe um console H2 com -web -webAllowOthers -webPort 8082 — um console administrativo do banco, acessível por qualquer host, sem senha configurada aqui. Aceitável numa máquina local isolada; se essa mesma classe for reaproveitada num servidor web sem alteração, isso expõe acesso direto ao banco (incluindo dados de paciente) na rede. Precisa ser removido ou travado antes de qualquer deploy, não é um ajuste de polimento.

Escolha de stack web

A pergunta não é "dá pra fazer" — dá, com qualquer framework Java. A pergunta é qual custa menos dado que a equipe já trabalha com Maven + Hibernate/JPA puro, sem experiência prévia documentada em nenhum framework web específico neste projeto.

A Spring Boot Recomendada

Maior ecossistema Java para REST + upload multipart + serialização JSON pronta. spring-boot-starter-data-jpa resolve de fábrica o problema do EntityManager por requisição (hoje o maior risco técnico da migração) via @Transactional, sem reescrever a camada de persistência na mão.

Custo: médio Tomcat embutido — não precisa de servidor externo
B Quarkus Não recomendada

Startup mais rápido e menor footprint de memória — vantagem real para microsserviços com autoscaling agressivo. Não é o gargalo aqui: é um serviço interno de um núcleo estadual, não uma API pública de alta escala. O ganho não paga a curva de aprendizado de um framework novo para a equipe.

Custo: médio-alto (curva de aprendizado)
C Servlet puro / Jakarta EE sem framework Não recomendada

Zero dependência nova além do já existente. Só até você precisar de upload multipart, roteamento e JSON — nesse ponto está reimplementando, na mão, o que Spring Boot já resolve testado.

Custo: baixo no início, alto depois Mais superfície para bugs próprios

Arquitetura proposta

Maven multi-módulo: o código de negócio atual (model, repository, service, util) sai para um módulo fillbpai-core, do qual tanto o desktop atual quanto o novo módulo web passam a depender. O desktop continua funcionando sem interrupção enquanto o web é construído em paralelo.

Fluxo de uma requisição de importação

ExcelImportService, ValidacaoPlanilhaService e AtendimentoImportacaoService já recebem String caminhoArquivo — o controller REST só precisa gravar o multipart recebido num arquivo temporário antes de chamar o mesmo código de sempre.

Endpoints típicos

POST /planilhas/analisar    (upload) → relatório de erros/avisos
POST /planilhas/importar    (upload) → importa para o banco
GET  /atendimentos?especialidade=&medico=
POST /bpa/gerar-completo    → download do .txt (Content-Disposition: attachment)
POST /bpa/gerar             (parcial, por especialidade/médico) → idem

Para isso, GeradorBPAiService precisa de um método novo que devolve os bytes do arquivo (ByteArrayOutputStream ou String) em vez de escrever direto no disco escolhido pelo FileChooser — os métodos atuais com Window continuam existindo, só passam a chamar esse método novo por trás em vez de duplicar a lógica de montagem do BPA-I.

Segurança e LGPD

Isto não é um item de checklist a mais — é a diferença central entre "roda numa máquina local" e "roda na rede". O fillBPAi manipula CPF, CNS, nome, telefone e endereço de pacientes. Hoje isso nunca sai do disco local de quem instalou o app. Num serviço web, esse dado passa a trafegar pela rede e fica acessível de qualquer lugar que alcance o servidor.

ItemHoje (desktop)Necessário no web
Autenticação Nenhuma — quem abre o app já está na máquina autorizada Login obrigatório antes de qualquer upload/download
Transporte Não se aplica (sem rede) HTTPS obrigatório, sem excessão
Console H2 -webAllowOthers, porta 8082, sem senha Removido do caminho de produção, ou preso a localhost com senha
Auditoria Não existe (uso individual local) Registro de quem importou/gerou o quê, e quando

Um repositório ou dois?

A Monorepo Maven multi-módulo (mesmo repositório) Recomendada

fillbpai-core compartilhado por fillbpai-desktop e fillbpai-web, todos no mesmo repositório git atual.

A lógica de negócio (layout BPA-I, validação de CNS/CEP/CPF, resolução de IBGE) é grande e muda com frequência — em dois repositórios, toda correção de regra precisaria ser replicada manualmente nos dois lugares, com risco real de divergência (o próprio bug de severidade do CNS_INVALIDO, corrigido recentemente, é o tipo de correção que teria que ser lembrada duas vezes). Um repo só resolve isso de graça, e o desktop continua funcionando normalmente enquanto o web é construído ao lado.

Histórico único por mudança de regra CI pode buildar só o módulo que mudou
B Repositórios separados Só se houver motivo organizacional

Faria sentido se o módulo web for construído por outra equipe (ex.: um time de desenvolvimento web terceirizado) ou exigir pipeline de deploy totalmente isolado do desktop. Nenhum desses cenários está colocado hoje — a decisão pode ser revisitada se isso mudar.

Custo: duplicação de regra de negócio Publicar fillbpai-core num repositório de artefatos (Nexus/GitHub Packages) para o outro repo consumir

Fases sugeridas

  1. Extrair fillbpai-core. Baixo risco — mover os pacotes model, repository, service, util para o módulo novo, ajustar pom.xml em módulos. O desktop passa a depender dele; nada de comportamento muda.

  2. Criar fillbpai-web com Spring Boot. Maior item de risco desta fase: EntityManager por requisição em vez do único compartilhado hoje. Segundo item: extrair de GeradorBPAiService um método que devolve bytes, sem depender de Window/FileChooser.

  3. Frontend web mínimo. Página de upload, relatório de erros/avisos, tabela de atendimentos com os mesmos filtros de hoje (especialidade, médico), botão de gerar e baixar o BPA-I. Maior esforço de reescrita do projeto todo — não há UI reaproveitável da versão desktop.

  4. Segurança antes de qualquer deploy real. Login, HTTPS, remoção/trava do H2 Console público. Não é polimento de fim de projeto — é pré-requisito para expor dado de saúde na rede.

Perguntas abertas

Antes de detalhar a implementação de qualquer fase, três decisões só cabem ao time/gestão do Núcleo de Telessaúde:

  • Hospedagem — servidor da própria SES-MS (on-premise, mais alinhado a LGPD para dado de saúde) ou nuvem?
  • Autenticação — usuários nominais próprios, ou integração com SSO/AD do governo estadual?
  • Convivência com o desktop — o app atual continua em uso em paralelo ao web, ou a ideia é substituir e descontinuar?
