Leitura de colunas por nome, não por posição

A planilha de atendimentos às vezes chega com colunas fora de ordem, ou com colunas extras que ninguém usa. Hoje o importador quebra nesses casos. Este documento propõe trocar a leitura posicional por um mapeamento de colunas pelo nome do cabeçalho.

Área: Importação de planilhas Excel Status: Proposta Data: 25/08/2026 Módulos afetados: ExcelImportService · ValidacaoPlanilhaService · AtendimentoImportacaoService · ColunaAliasUtils (novo) · tela de configuração (nova)
Contexto Objetivo Opções Recomendação Casos extremos Plano Testes

Contexto

ExcelImportService.importarLinha() lê cada célula por índice fixo — row.getCell(0) até getCell(23) — assumindo que as 24 colunas sempre chegam na mesma ordem. ValidacaoPlanilhaService.validarEstrutura() confere o cabeçalho contra COLUNAS_ESPERADAS, mas também posição a posição: cabecalho.getCell(i) comparado com COLUNAS_ESPERADAS[i].

O problema aparece quando uma coluna extra é inserida no meio da planilha, ou duas colunas trocam de lugar: tudo que vem depois do desvio desalinha, e a validação gera erros em cascata mesmo quando os dados em si estão corretos. O resultado prático é bloqueio total da importação, e o usuário precisa reordenar a planilha manualmente antes de tentar de novo.

Objetivo

Passar de leitura posicional para leitura por nome de coluna: a ordem das colunas deixa de importar, e colunas extras não usadas são simplesmente ignoradas.

Opções consideradas

A Mapa de colunas por nome do cabeçalho Recomendada

Ler a linha de cabeçalho uma vez por planilha, construir um Map<String, Integer> (nome normalizado → índice), e usar esse mapa para buscar cada célula pelo nome em vez do índice fixo.

Colunas fora de ordem são resolvidas automaticamente pela busca por nome; colunas extras nunca são procuradas no mapa, então são ignoradas sozinhas; e uma coluna obrigatória ausente vira um erro único e específico no momento de montar o mapa, em vez de uma cascata de divergências posicionais.

Custo: médio Reaproveita a normalização de texto já existente
B Reordenar a planilha em memória antes de processar Não recomendada

Detectar a ordem real das colunas pelo cabeçalho e reescrever as linhas na ordem esperada antes de chamar importarLinha.

Custo: médio-alto Mesmo resultado da Opção A, com mais código
C Tolerância posicional com fallback por nome Não recomendada

Manter a leitura posicional e, só se a validação do cabeçalho falhar, tentar localizar cada coluna esperada por nome antes de desistir.

Custo: dois caminhos de código Mais superfície para bugs, mais difícil de testar

Recomendação: Opção A

1. Novo mapeamento canônico

Trocar COLUNAS_ESPERADAS — hoje um array posicional — por uma estrutura em memória que associe nome canônico do campo a nome(s) aceitos no cabeçalho. Diferente da primeira versão deste runbook: essa lista de aliases não fica hardcoded no Java — é carregada de um arquivo externo, editável sem recompilar (ver seção 6). 

Map<String, List<String>> aliases = ColunaAliasUtils.carregarAliases();
// aliases.get("CPF_PACIENTE") → ["CPF DO PACIENTE", "CPF PACIENTE", ...]

Usar listas de aliases, não só um nome, absorve variações de texto que a planilha de origem já mostrou no passado — por exemplo "CBO DO MEDICO" vs. "CBO MEDICO" — sem quebrar nada, e sem exigir alteração de código quando aparecer uma variação nova.

2. mapearColunas(Row cabecalho)

Método novo, em ExcelImportService ou numa classe pequena PlanilhaColumnMapper: percorre as células do cabeçalho, normaliza cada uma (reaproveitando normalizarTexto — remove acento, uppercase, trim) e constrói Map<colunaCanonica, indice>. Para cada entrada de COLUNAS_OBRIGATORIAS não encontrada, gera um ErroValidacao bloqueante — um erro por coluna faltante, não mais uma cascata. Colunas do cabeçalho sem correspondência canônica podem ser logadas como informativo, só para deixar visível que estão sendo ignoradas de propósito.

3. importarLinha passa a receber o mapa

public LinhaImportacaoDTO importarLinha(Row row, Map<String, Integer> colunas) {
    dto.setTipoServico(getString(row, colunas, "TIPO_SERVICO"));
    dto.setCep(getString(row, colunas, "CEP"));
    // ...
}

4. Os dois pontos que chamam o serviço

ValidacaoPlanilhaService.validar() e AtendimentoImportacaoService já leem sheet.getRow(0) antes do loop de linhas — é o lugar natural para chamar mapearColunas uma vez e reutilizar o resultado em cada chamada de importarLinha dentro do loop.

5. validarEstrutura simplificada

Deixa de comparar posição por posição — passa a apenas checar que todas as colunas de COLUNAS_OBRIGATORIAS foram encontradas em mapearColunas, na ordem em que estiverem.

6. Onde e como os aliases são administrados

A primeira versão deste runbook sugeria um Map hardcoded no Java para os aliases. Essa ideia parte de uma premissa que não se sustenta: o fillBPAi roda na ponta, em máquinas de outras unidades de saúde, e quem usa o sistema não tem acesso ao código-fonte nem forma de recompilar. Uma variação de nome de coluna nova exigiria abrir uma issue, esperar uma nova versão e reinstalar — inviável no dia a dia do Núcleo de Telessaúde.

A1 Map hardcoded no Java Descartada

Exige recompilar e reinstalar o app para cada alias novo — inviável para usuários sem acesso ao código.

A2 Arquivo CSV externo, sem tela no app Alternativa simples

Sem recompilar, mas o usuário precisa localizar o arquivo no disco e editá-lo manualmente, respeitando um formato de texto — a mesma fricção que outras rotinas do projeto já evitam com uma tela dedicada.

A3 CSV externo + tela de configuração no app Recomendada

O mesmo arquivo CSV da opção A2 por baixo, mas administrado por uma tela dentro do fillBPAi — sem editar arquivo à mão, sem recompilar.

Reaproveita um padrão que já existe no projeto

Padrão já existe no projeto

CnsProfissionalUtils já resolve exatamente este problema para o CNS dos profissionais: carrega dados/medicos_cns.csv do classpath e de um arquivo externo (carregarDeClasspath + carregarDeArquivoExterno), expõe salvar(nome, cns) para persistir uma entrada nova e obterTodosRegistrados() para listar tudo o que está cadastrado. Um ColunaAliasUtils no mesmo molde — trocando o formato nome;cns por campoCanonico;alias em dados/colunas_aliases.csv — reaproveita esse padrão em vez de inventar um novo.

7. Duas camadas de aliases: padrão e local

O fillBPAi roda em várias unidades de saúde, cada uma com suas próprias pequenas variações de planilha — e o ajuste que uma unidade precisa não tem por que aparecer nas outras. Em vez de tratar isso como limitação, dá para desenhar como duas camadas explícitas, na mesma lógica de precedência que CnsProfissionalUtils já usa (classpath primeiro, depois arquivo externo sobrescrevendo/complementando):

CamadaOnde moraQuem mantémQuando muda
1 · Padrão dados/colunas_aliases.csv no classpath, versionado no git Equipe do fillBPAi A cada release — quando um alias local se mostra útil em mais de uma unidade, é promovido para o padrão
2 · Local dados/colunas_aliases.csv externo, só naquela instalação A própria unidade, pela tela de configuração A qualquer momento, sem depender de nova versão do app

É o mesmo comportamento que já existe hoje para o CNS dos profissionais: o comentário de carregarDeArquivoExterno() já descreve o arquivo externo como uma forma de "capturar entradas adicionadas pelo pré-cadastro que ainda não foram recompiladas no classpath" — ou seja, o caminho de promoção de local → padrão já é uma ideia prevista no código, só nunca foi formalizado como processo. Para os aliases de coluna, vale adotar o mesmo: o time revisa os arquivos locais periodicamente (ou pede que a unidade compartilhe o CSV quando um alias novo aparecer) e incorpora ao dados/colunas_aliases.csv do classpath na próxima release.

8. Modelo de tela

Uma única tela de Configurações, organizada em abas — hoje só a de colunas, com a aba de CNS dos médicos reservada para quando o cadastro que já existe em CnsProfissionalUtils ganhar interface própria. As duas abas compartilham o mesmo desenho: lista de itens à esquerda, aliases da seleção à direita.

Casos extremos

CasoComo resolver
Cabeçalho com nome duplicado (duas colunas "CEP") Ambíguo — reportar como erro estrutural explícito em vez de silenciosamente usar a primeira ou a última ocorrência.
Coluna obrigatória totalmente ausente Um erro bloqueante único, apontando o nome canônico esperado — já é o comportamento atual para planilha sem cabeçalho, só fica mais preciso.
Nomes de cabeçalho ligeiramente diferentes de planilha para planilha Resolvido pela lista de aliases em COLUNAS_OBRIGATORIAS, sem precisar tocar em código de leitura.

Plano de implementação

  1. Extrair normalizarTexto para uma classe utilitária compartilhada — hoje é privado em ValidacaoPlanilhaService, e vai ser usado tanto na validação quanto no mapeamento de colunas.

  2. Criar ColunaAliasUtils, no mesmo molde de CnsProfissionalUtils: carrega dados/colunas_aliases.csv (classpath + arquivo externo), expõe salvar(campo, alias), remover(...) e obterTodosRegistrados().

  3. Criar PlanilhaColumnMapper com mapearColunas(Row) → Map<String, Integer>, usando os aliases carregados por ColunaAliasUtils.

  4. Alterar ExcelImportService.importarLinha para aceitar o mapa. Manter a assinatura antiga só se algum outro chamador depender dela — hoje só ValidacaoPlanilhaService e AtendimentoImportacaoService chamam.

  5. Atualizar os dois chamadores para montar o mapa uma vez, a partir de sheet.getRow(0), e passá-lo no loop.

  6. Simplificar validarEstrutura para usar o novo mapa em vez de comparação posicional.

  7. Criar a tela "Configurar Colunas da Planilha" (Dialog JavaFX, mesmo padrão do dialog de "Selecionar Mês"): lista os campos canônicos com os aliases cadastrados e permite adicionar/remover, chamando ColunaAliasUtils por trás.

  8. Testar manualmente com três planilhas — formato atual, colunas trocadas de posição, coluna extra inserida — e testar o fluxo completo de cadastrar um alias pela tela nova e confirmar que a importação seguinte já reconhece.
